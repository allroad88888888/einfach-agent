# 上下文缓存回归：第二批只读测试现象记录

日期：2026-08-04

模型：`deepseek-v4-flash`

会话：`35e8544e-c280-4c71-a7d3-bd8b66e01ae6`
完成 run：`95a0307a-544a-4e3e-a96a-0e5c3f47a9be`

## 目的

验证大上下文超过成本软上限后，压缩投影是否会保住已经发送过的前缀；同时观察 DeepSeek 返回的真实缓存用量，而不是用本地估算代替供应商数据。

## 测试方式

同一会话连续执行两批只读文件读取。第一批建立大上下文，第二批继续追加只读读取请求。测试 Agent 只调用 `read_file`，每次均指定 `maxBytes: 200000`；不修改文件、不创建 worktree、不执行 shell、不提交。

本记录只统计完成 run 中 `status='ok'` 的 8 个 `llm.chat` span。缓存命中/未命中 token 直接取模型响应的 usage 字段。

## 关键现象

第 6 轮发生了一次“增量尾部压缩”，不是重新压缩整段历史：

- 既有稳定投影：123,379 tokens。
- 新增历史：52,908 tokens，压缩为 43,258 tokens。
- 该轮最终上下文估算：166,967 tokens，位于 173,333-token 有效预算内。
- 第 7、8 轮继续复用这份投影，估算上下文分别为 168,015 和 169,543 tokens。

因此，“新增内容溢出预算时把旧压缩投影整体改写”的路径已经没有发生。`llm.context_projection_extended` 在第 6 轮留下了可审计事件，随后两轮均有 `llm.context_projection_reused` 事件。

## 结论

增量压缩实现本身已生效：旧前缀没有在第 6 轮被全量重写，后续请求确实复用了同一份本地投影。

但这还不能视为缓存优化验收通过。供应商返回的命中率在 0.99% 到 99.92% 之间大幅波动，即使本地投影复用，仍出现了多轮几乎全量未命中。加权命中率为 41.85%，低于现有 63.9% 的历史基线，也无法满足“稳定消除低命中轮”的目标。

这说明原先“每轮全量重压必然导致低命中”的问题已被部分消除，但仍有独立因素让 DeepSeek 的实际前缀缓存失效。

## 同时发现的可观测性问题

本地 `ContextCacheTracker` 从第 3 轮起每轮都把 epoch 原因标为 `compaction_projection_changed`，epoch 从 2 连续增长到 7；但同一批轨迹实际已经记录了投影复用和增量延伸。

这两个信号相互矛盾：压缩插件说明稳定投影仍被复用，tracker 却把请求归因为投影改变。它不会改变实际发给模型的请求，但会误导 UI/trace 对缓存失效的归因，不能再把该字段直接当作供应商缓存失效证据。

## 后续排查

1. 为请求投影加入仅含长度与内容哈希的逐 item 前缀诊断，确认供应商实际收到的稳定前缀是否逐字一致；不记录原文。
2. 修正 `ContextCacheTracker` 的归因：稳定压缩投影后只追加事实历史时，应保持同一 epoch，而非持续标记 `compaction_projection_changed`。
3. 用相同的只读脚本连续跑至少 3 次，对照每轮 `cache_hit_tk` / `cache_miss_tk` 与 DeepSeek 控制台账单导出。首个验收门槛为加权命中率恢复到不低于 63.9%，并且增量压缩后的连续复用轮不再出现约 1% 的全量未命中。
