# 线：宿主分流与应用装配

一句话：同一份 core 在不同宿主下要选一套不同的实现，这条线把「当前是哪一态」收敛成一次握手、再按那一个结论把所有实现一次分派到底。
类型：主线

## 入口（一个实例从哪开始；引 file:line）

- `apps/web/src/main.tsx:199` —— `export const started = startApplication()`。浏览器侧唯一入口，`index.html` 只 import 这个模块；导出 promise 是给测试等装配完成用的，生产无消费方（`main.tsx:194-198`）。
- `apps/web/src/main.tsx:141` —— `const host = await resolveHost()`。**全仓生产代码里宿主探测的唯一一次调用**（下面「数出来」有计数）。
- `apps/cli/src/bootstrap.ts:62` —— CLI 的 `main()`；它**不调用 `resolveHost()`**，装配走 `apps/cli/src/runtime.ts:115` 的 `assembleCliRuntime`。
- `apps/server/src/main.ts:7` → `apps/server/src/mainRunServer.ts:54` —— Node 后端进程入口；它不是 core 的装配点，是 `server` 这一态背后那台机器。

## 数据怎么走（逐步；每步引 file:line）

1. **声明宿主态** —— `apps/web/src/host/resolveHost.ts:161` `resolveHost()` 发一次 `GET /api/health`（路径常量 `serverHealthContract.ts:21`），2 秒超时（`resolveHost.ts:65`），`AbortController` + `Promise.race` 双保险（`resolveHost.ts:139-154`）。载荷必须同时满足 `service==='einfach-agent'`、`host==='node-server'`、`platform` 属四值域，否则不认（`serverHealthContract.ts:65-71`）。返回可辨识联合：`{kind:'server', platform}` 或 `{kind:'static', reason}`，reason 四值仅供诊断（`resolveHost.ts:38-50`）。**任何失败都落 `static`**，包括「永不返回」。
2. **注册命令桥** —— `main.tsx:142` `registerHostCommandBridge(host)`。`server` 支先同步收走 URL 里的 token（`hostCommandBridge.ts:60`，把它从地址栏抹掉，见 `serverInvokeToken.ts:116-125`），再 `configureHostInvoke({ loader: async () => httpInvoke, platform: host.platform })`（`hostCommandBridge.ts:61`）。`static` 支**什么都不登记**（`hostCommandBridge.ts:63-64`）。core 侧收的是 loader 不是已解析的 invoke，登记因此同步生效、不留 `hasHostBridge()` 仍为 false 的窗口（`packages/agent-core/src/runtime/hostBridge.ts:34-45`）；平台是同一次登记的必填字段（`hostBridge.ts:58-62`）。
3. **触发 / 选实现** —— `main.tsx` 按已解析的那一个 `host` 逐个装：标准工具与 skills/plan/delegation 槽 → MCP → 用户插件（`host.kind!=='server'` 直接 return）→ 凭据宿主 → 模型传输 → `configureCommands` 把 server 的受管标记或 static BYOK 的内存 Key 与 fetch 一起交给 core。
4. **执行 / 读写** —— `main.tsx:114-132` `bootstrapApplication(host)`：`core.persistence.configure({...await createHostPersistenceDrivers(host)})`（117-122 → `persistence/persistenceDrivers.ts:64`）→ 刷盘时机（`main.tsx:123` → `hostRecoveryFlush.ts:15`）→ 观测 driver（`main.tsx:124` → `hostObservability.ts:62`）→ `core.persistence.hydrate()`，没恢复出会话才 `newSession()`（125-126）。运行期每次本机能力调用是 `apps/web/src/host/serverInvoke.ts:148` 的 `POST /api/invoke/<command>`；SQL 是同一条路由的两条命令（`persistence/serverSqlExecutor.ts:46-47`）。
5. **结果去哪** —— `main.tsx:191` `renderApp(await bootstrapApplication(host), credentialHost.available)`：第二个参数决定启动凭据门禁开不开，判据是「这个宿主管不管得了凭据」而不是宿主品牌（`main.tsx:84-89`）。服务端那头，一条 `/api/*` 请求先过 `requestRouter.ts:86` 的认证卡口，再分派到 invoke / model / events / health 四条（`requestRouter.ts:93-115`），最后落到 `packages/host-node` 的路由表（`createServer.ts:98`、`createNodeHostInvoke.ts:117-137`）。

## 形状（分支线：目录/文件形状 + 计数；必需 vs 可选）

- **宿主态**：`HostKind = 'server' | 'static'`，**2 态**（`resolveHost.ts:29`）。外加一条**正交**的构建模式轴 `import.meta.env.DEV`，全仓非测试代码只出现 2 次（`hostModelTransport.ts:28`、`hostObservability.ts:69`）。CLI 是**第三条装配路径**、不是第三态：它压根不经过 `resolveHost()`。
- **判定函数调用点**：`resolveHost()` 生产调用 **1 处**（`main.tsx:141`）；另有 10 个非测试文件只 `import type { ResolvedHost }`。`configureHostInvoke()` 生产调用 **2 处**（`hostCommandBridge.ts:61`、`cli/runtime.ts:111`）。
- **有没有第二处重新探测宿主**：**没有**。CLAUDE.md:110「装配点不自己探宿主」核过成立——9 个分流点全部收 `host` 形参。core 里 `hasHostBridge()` 被 **15** 个非测试文件消费（`packages/agent-core/src/runtime/` 下，其中 13 个是注释点名的那批），它问的是「登记过桥没有」，不是宿主品牌。
- **分流点 9 个**（收 `ResolvedHost` 并分支的函数）：`host/` 下 5 个（bridge / transport / credential / observability / flush）+ `persistence/persistenceDrivers.ts:64` + `mcp/initialize.ts:73` + `mcp/toolNameCacheStorage.ts:175` + `plugins/initialize.ts:83`。
- **文件计数（git 跟踪）**：`apps/web/src` 304，其中 `host/` 18（9 源 + 9 测试）、`modelTransport/` 14（8 源 + 6 测试）；`apps/server/src` 71（34 源 + 37 测试/harness）；`apps/cli/src` 22；`packages/host-node/src` 8 个子目录 + 9 个根文件。
- 必需：每加一态，9 个分流点都要给出一支（`switch` 上穷举的有 4 处：`hostCommandBridge.ts:51`、`mcp/initialize.ts:53`、`mcp/toolNameCacheStorage.ts:176`、`persistenceDrivers.ts:67` 是 if 形态）。可选：`static` 支可以是「什么都不装」。

### `/api/*` 的四道防线（核过；顺序确实如此，默认拒绝）

一道门，位置在 `apps/server/src/requestRouter.ts:86` —— **认证在路径分派之前**，所以 `/api/invok` 拿到的是 401 不是 404（`requestRouter.ts:9-10`）。判定全在 `apps/server/src/authGuard.ts:100-123`，逐条：

1. `authGuard.ts:101` 回环对端地址（`isLoopbackAddress`，读的是 socket 事实，伪造不了 —— `authGuard.ts:91-97`）→ 403 `non_loopback_client`。
2. `authGuard.ts:104` Host 头必须是本服务（`isHostHeaderThisServer`）→ 403 `forbidden_host`（DNS rebinding 的落点）。
3. `authGuard.ts:108` Origin 判定 → 403 `forbidden_origin`；**缺席放行**，理由写在 `authGuard.ts:18-27`。
4. `authGuard.ts:111` `/api/health` 在此**豁免 token**（且仍受前三道管），裁决与代价在 `authGuard.ts:29-43`；其余走 `authGuard.ts:112-122` → 401 `missing_token` / `invalid_token`，带 `www-authenticate: Bearer`。

默认拒绝是结构性的：`createServer.ts:113` 在没传 token 时**照样生成一枚随机 token**（没人知道 → 全部 401），文件里没有 `disableAuth` 这类开关（`createServer.ts:66-72`）。第五道「免费防线」是 `content-type: application/json` 要求（`modelRoute.ts:100`、`invokeRoute` 同款），跨站 `<form>` 设不出它。

### CLI 与浏览器怎么共用 host-node，哪些不共用

共用的是**同一张命令路由表**：`createNodeHostInvoke(options)` 合成 14 个域 registrar（`createNodeHostInvoke.ts:117-137`），30 条命令、命令全集是唯一权威（`commandNames.ts:3`）。浏览器经 HTTP（`createServer.ts:98` 建表 → `invokeRoute.ts` 逐字透传 args → `invokeRouteCommandName.ts:35` 只取名不校验合法性），CLI 进程内直连（`cli/runtime.ts:107`）。两条路上 core 侧完全一样：`configureHostInvoke({loader, platform})`，之后 core 只问 `hasHostBridge()`。

**不共用的东西**（都核过）：

- **认证与传输壳**：token 链路（`serverInvokeToken.ts`）、四道防线、body 上限（`invokeRoute.ts:40` 32 MiB / `modelRoute.ts:78` 56 MiB）只在 HTTP 那条路上；CLI 进程内没有这一层。
- **失败形状**：HTTP 那条要把 `ServerInvokeError` 折成裸字符串以对齐历史契约（`serverInvoke.ts:193-201`）；CLI 拿到的是 `NodeHostCommandError` 原件（`createNodeHostInvoke.ts:97`）。SQL 那条为此**绕开** `httpInvoke` 改用 `invokeServerCommand`（`serverSqlExecutor.ts:26-31`）。
- **事件反向通道**：`server` 建 `createHostEventBus` 并把发射面注入桥（`createServer.ts:97-101`），经 `GET /api/events` 的 SSE 出去（`eventsRoute.ts:27`，客户端用 fetch+ReadableStream 而不是 `EventSource`，理由 `eventsRoute.ts:8-41`）。**CLI 不传 `emitHostEvent`**（`cli/runtime.ts:107`），按 `hostOptions.ts:39-40` 事件被丢弃。
- **模型转发**：`server` 有 `POST /api/model/request` 直调 `forwardProviderRequest`（`modelRoute.ts:46`，刻意不进 `/api/invoke` 的 JSON 信封 —— `modelRoute.ts:3-8`）；CLI 直接用 `globalThis.fetch` 打厂商（`cli/runtime.ts:139`），不经 host-node 的端点白名单。
- **凭据**：`server` 侧 Key 由后端读写 `~/.webAgent/config.json`（`host-node/src/config/configPaths.ts:44`）；CLI 自己解析环境变量 + 同一份文件（`cli/credentials.ts:104-129`），两条各读各的。
- **持久化**：`server` 有；CLI 没有（见「漂移」#2）。
- **主目录权威**：`server` 由 `--` 选项/默认透传（`createServer.ts:99` 的 `homeDir`）；CLI 自己 `homedir()` 解析一次再注入（`cli/runtime.ts:121-122`），并直接拿它当用户级 skills 根（`cli/runtime.ts:129`）。

## 标准之外

### 另一类（同目录、不同机制）

- `apps/web/src/host/` 的 9 个非测试文件里只有 **5 个是分流面**；另 4 个（`serverInvoke.ts`、`serverInvokeToken.ts`、`serverHealthContract.ts`，加上 `resolveHost.ts` 自己）是 **`server` 这一态的客户端零件**——HTTP 客户端、token 链路、握手契约副本。它们不收 `ResolvedHost`，别照分流面的形状读。
- `apps/web/src/modelTransport/` 的 8 个非测试文件里只有 **3 个是 transport 实现**（server / devPreview / unavailable）；另 5 个（`providerFetch`、`providerRoute`、`providerWireBody`、`providerWireEnvelope`、`modelEndpoint`）是三条路共用的编码与白名单零件，不是分流点。

### 其实合规（看着像违规，核过是对的）
