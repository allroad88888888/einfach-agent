# 线：工具家族

一句话：一个「模型能调的工具」是一个自带 JSON Schema 与说明书的纯声明对象，由所属域的 registrar 装进某个 `CoreInstance` 私有的 `ToolRegistry`，此后它的发现、加载、确认与执行全由 core 的运行时代办。

类型：分支线——挂在主线的 `packages/agent-core/src/runtime/toolCallBatch.ts:47`（`runToolCallBatch`，运行时）与 `tools/<域>/src/index.ts:register<Domain>Tools`（编辑/配置时）。

## 入口（一个实例从哪开始；引 file:line）

- 声明：`tools/<域>/src/<工具名>/<工具名>.ts` 导出一个 `Tool` 常量。契约在 `packages/agent-core/src/tools/types.ts:287-308`。奠基样例 `tools/fs/src/read-file/read-file.ts:105`。
- 注册：域 registrar `tools/fs/src/index.ts:30-46`（`registerFsTools`）；六域由 meta 包一次装齐 `tools/standard/src/index.ts:34-41`。
- 装配：`apps/web/src/main.tsx:144` 与 `apps/cli/src/runtime.ts:14` 各自对 `core.tools` 调一次 `registerStandardTools`。**core 不自动装工具**（`packages/agent-core/src/runtime/core/coreInstance.ts:198-202`）。
- 第七域 MCP 单独装：`apps/web/src/mcp/toolProbeWiring.ts:117` 调 `registerMcpTools(registry, { manager, lastKnownTools })`（`tools/mcp/src/index.ts:48-58`）。CLI 不装 MCP。

## 数据怎么走（逐步；每步引 file:line）

1. **声明** → `Tool` = `name` + `runtime`（`internal`/`browser`/`server`，`types.ts:26`）+ `skill`（`description`/`triggers`/`content`，`types.ts:63-67`）+ `inputSchema` + 可选 `callTiming`/`replayUnsafe`/`execution` + `execute(args, ctx)`。guide 正文用 `import guide from './x.md?raw'`（`tools/fs/src/read-file/read-file.ts:9`；类型声明 `tools/fs/src/raw-modules.d.ts`；tsup 侧内联插件 `tsup.preset.ts:87-89`）。
2. **注册** → `registry.register(tool)`：同名后注册覆盖，每次签发单调 `registrationVersion`（`packages/agent-core/src/tools/toolRegistry.ts:100-106`）。`origin:'external'` 且带 `callTiming` 的会被就地剥除并记诊断（`toolRegistry.ts:71-77`）。到点工具同时进按 timing 分桶的注册簿（`runtime/timedToolRegistry.ts:20-23`，由 `coreInstance.ts:200` 包住 registry）。
3. **可见性过滤**（两道，判据同源）：
   - 到点工具整类不进模型面：`isModelVisibleTool = !tool.callTiming`（`packages/agent-core/src/tools/toolCatalog.ts:15-17`），`list()` 与 `loadSchema()` 都过它（`toolRegistry.ts:130-136`、`152-158`）。
   - `runtime:'server'` 的工具要求宿主有本机命令桥：`isToolVisible(runtime, hostHasLocalCapabilities)`（`runtime/turnToolVisibility.ts:54-56`），总闸源头是 `hasHostBridge()`（`runtime/modelTurnPrefix.ts:60`）——**不是宿主品牌**。
4. **工具摘要文本** → `availableToolSummaries` 排掉 `request_tool_schema` 与不可见项并稳定排序（`turnToolVisibility.ts:58-72`）→ `buildToolManifestText` 渲成 `· name [runtime] — description` 的清单，进稳定 system 前缀（`runtime/toolManifest.ts:58-73`，装配点 `modelTurnPrefix.ts:62-65`）。摘要只含 name/description/runtime，**不含 schema 与 guide**。
5. **lazy schema** → 顶层 tools 数组恒含元工具 `request_tool_schema`（`runtime/turnToolSet.ts:120-158`），其余槽位是本轮已加载的工具（`turnToolSet.ts:98-115`，容量 = provider 上限 − 1，LRU 见 `touchRecentToolName` 33-46）。模型调它：给 `toolName` 就 `loadSchema` 补 `inputSchema + guide`（`toolCallGate.ts:153-158`，投影 `toolCatalog.ts:49-56`）；省略 `toolName` 就返回有界可搜索的 manifest 分页（`toolManifest.ts:117-177`）。直接点名未加载工具会被闸门就地转成一次自动加载（`toolCallGate.ts:125-135`）。
6. **执行前** → `runToolCallBatch` 逐个调用：解析 args → `handleToolGate`（`toolCallGate.ts:72`）→ 风险分级 `classifyToolRisk`（`runtime/dangerousTools.ts:18-28` 是危险工具名单）→ 需要确认就把 run 置 `waiting_confirmation` 并返回（`toolCallBatch.ts:125-126`、`170`）。全批都是 `execution.mode:'parallel'`、参数合法且不需确认时才并发（`toolCallBatch.ts:64-68`）。
7. **执行** → `executeToolCall` 造 ctx 再交给 registry：`base.core.tools.run(name, args, buildToolContext({...}), registrationVersion)`（`runtime/toolCallExecutor.ts:38-49`）。`run` 的生命周期：未知名回 error 不抛 → 版本不匹配 fail-closed → schema 校验（失败回 error，不进 execute；成功用规范化值）→ `await execute` → 钳位告警附回结果 → `AbortError` 透传、其余封成 error result（`toolRegistry.ts:168-219`）。
8. **结果去哪** → `appendMappedToolResult` 把三态映射成一条 `role:'tool'` transcript item（`runtime/toolLoopSupport.ts:81-86`，落地 `:69`），随后 `requireRecoveryDurability` 落盘。`{pause}` 不回填，改置 `waiting_user` / `waiting_plan_approval`（`toolCallBatch.ts:181-194`）。

## 每部分负责什么 / 状态归谁 / 谁能调谁

| 部分 | 职责 | 持有的状态 | 谁可以调它 | 不许做 |
|---|---|---|---|---|
| `tools/<域>/src/<工具>/` | 声明一个 `Tool`：schema、说明书、纯 execute | 无（模块级常量；需要运行时依赖的用工厂闭包，见 `tools/mcp/src/index.ts:48`） | 只被本域 registrar import | import store/atom；import 宿主 API；自己做 workspace 解析或确认 |
| `tools/<域>/src/index.ts` | 桶文件 + `register<Domain>Tools` | 无 | meta 包、应用装配层 | 反向依赖 core 之外的包 |
| `tools/standard` | meta 聚合，一次装齐六域 | 无 | 应用与测试入口 | 收录 mcp 域 |
| `ToolRegistry` | 注册 / 懒加载 / 统一分发 | `Map<name,{tool,version}>` + 每名最后版本 | core 运行时、装配层 | append timeline、判 ghost/stale（`toolRegistry.ts:14-16`） |
| `ToolCatalog` 快照 | 冻结一个 run 的工具集 epoch | 冻结的成员 + 版本 | `runtime/toolEpoch.ts` | 随 registry 变化 |
| `buildToolContext` | 造并守卫工具的唯一副作用面 | 无（读写都经传入的 `CoreInstance`） | `toolCallExecutor`、`timedDispatch`、子 agent 循环 | 让 `callTool` 的 pause 冒泡（`toolContext.ts:115-120`） |
| `runToolCallBatch` | 闸门、风险、确认、并发、回填 | run 状态（经 `patchRun`） | 主循环 | 绕过 registry 直接 `tool.execute` |

**为什么工具不能直接碰 store**：ToolContext（`types.ts:169-284`）是白名单式的副作用面——`progress`/`callTool`/`runShell`/`readWorkspaceFile`…/`renderCard`/`saveArtifact`/`skills`/`delegateAgents` 等，全部由 `runtime/toolContext.ts:106-114` 在**一处**装配，workspace root 解析（`:81`）、跨 workspace 只读权限（`:84-85`，且刻意不进 schema，防模型伪造）、ghost/stale 守卫（`:87`）、互调防环限深（`MAX_TOOL_DEPTH = 4`，`:45`、`:115-120`）都集中在这里施加。工具自己 import atom 等于开一条绕过这全部守卫的通道，而门禁 `scripts/check-boundaries.js:23-41` 只挡「core/能力包 → tools」的反向依赖，挡不住这条——靠的是 core 公开面白名单（`check-boundaries.js:17-19`）加约定。实测生产代码里 `tools/*/src` 对 core 的 import 全部落在 `core/tools`(111)、`core/skills`(12)、`core/planning`(8)、根 barrel(3 处，仅取类型)、`core/subagents`(1)。

**callTiming（到点工具）与普通工具的区别**：普通工具由模型点名调用；到点工具由宿主在九个核心时机（`packages/agent-core/src/tools/toolCallTiming.ts:12-21`）分派，**整类不进发现面、不进 `request_tool_schema`、不进 tools 数组**。分派器另有一条通道（`runtime/timedDispatch.ts`），并且因为**不经过确认门**，执行前必须先咨询风险评估、非 safe 一律拒绝（约定写在 `toolCallTiming.ts:5-10`）。当前仓库里唯一的到点工具是 `skill_manifest`（`tools/skills/src/skill-manifest/skill-manifest.ts:17`，`sessionStart`）。

## 标准之外

### 另一类（同目录、不同机制）

- `tools/mcp`（1 个工具目录 + 约 25 个模块）——**另一类**，三条机制都不同：① registrar 签名是 `registerMcpTools(registry, dependencies)`，缺依赖在装配期就抛（`tools/mcp/src/index.ts:48-54`）；② 不在 `registerStandardTools` 里，由应用层单独装（`apps/web/src/mcp/toolProbeWiring.ts:117`），CLI 完全不装；③ 真正给模型的工具**不是源码里的常量**，而是连上服务后按远端清单现造并动态 register/unregister（`tools/mcp/src/toolAdapter.ts:388-403`），未连接服务还会造「占位工具」（`tools/mcp/src/placeholderTool.ts:1-16`）。所以它是「第七域」，不是标准包漏收。
- `tools/skills/src/skill-manifest/`——**另一类**：到点工具（`callTiming:'sessionStart'`，`skill-manifest.ts:17`）。没有 `.md` 是机制决定的：guide 只随 `request_tool_schema` 发出，而到点工具永远不进那条路（`toolCatalog.ts:15-17`），所以 `skill.content` 内联一句话（`:20`）。计数 1。
- `tools/skills/src/planning/`——**另一类**：根本不是工具目录，是内置 skill `planning` 的 L3 资源树（`tools/skills/src/registry.ts:28` 用 `?raw` 引入 `./planning/references/evaluation.md`）。只因为它恰好是 `src/` 下的一层目录才落进枚举。计数 1。

### 漂移 / 遗留（少、晚、不合形状——引用并说明；是「别模仿」不是「删」）

### 待确认（≤5；只问改变新代码去向的；点名成员；每条两种解释）

1. **计划域三个工具的测试粒度**（`tools/planning/src/create-plan/`、`execute-plan/`、`update-plan/`；对照 `tools/planning/src/planToolDurability.test.ts:4-7`）：A 约定就是「每工具一份同目录测试」，这三个是欠债，**新工具一律补同目录测试**；B 计划工具是 `PlanRuntime` 的薄壳，域级不变量测试才是对的粒度，**新的计划工具照此办理、不写同目录测试**。
2. **到点工具要不要写 `.md`**（`tools/skills/src/skill-manifest/skill-manifest.ts:20`）：A `.md` 的用途只是模型 guide，到点工具永远发不出去，内联一句话即可，**新到点工具都不写 `.md`**；B `.md` 同时是给人读的工具说明，缺它是漏写，**新到点工具照样要补**。
3. **新工具要不要同步改 `tools/standard/src/index.ts`**（`:4,6,30` 的「6 域 31 工具」计数注释；对照 `tools/standard/src/index.test.ts:12-41` 的权威清单）：A 只改 `index.test.ts` 的清单，`index.ts` 的计数注释是会过期的装饰、不必维护；B 两处都改，计数注释是这份清单的对外说明、必须与断言同步。
4. **MCP 动态造出的工具要不要打 `origin:'external'`**（`tools/mcp/src/toolAdapter.ts:388-403` 未打；`packages/agent-core/src/tools/toolRegistry.ts:71-77` 只对打了标的剥 `callTiming`）：A 有意——MCP 自己构造 `Tool` 字面量、结构上不可能带 `callTiming`，标记是留给未来第三方注册面的，**新的动态提供方也不必打**；B 漏打——TOOLS-SPEC.md:83 点名「外部声明工具（如 MCP 清单）」，那道保护现在对 MCP 恒不生效，**新的动态提供方必须打上**。
