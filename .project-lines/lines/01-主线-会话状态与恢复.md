# 线：会话状态、事务日志与恢复

一句话：一个会话的运行态住在它自己的 einfach store 里，每次写入经收口的写入器同时改 store 并记一笔账，账与快照在同一个耐久性栅栏成对落盘，重启时按 generation 配对铺回来。

类型：主线

## 入口（一个实例从哪开始）

- **会话槽的诞生**：`packages/agent-core/src/runtime/core/coreInstance.ts:157-165` —— `createSessionStore(id)` 一次造出 `{ id, store, history }`。`store` 是 `createStore()`，`history` 是 `createSessionHistory(store)`。**建日志与登记 applier 是同一件事**（`packages/agent-core/src/state/sessionHistory.ts:56-58` 穷举遍历 `SESSION_SLOT_KEYS` 注册），理由写在同文件 `:1-7`：`record()` 碰到未登记的 key 会抛，两件事分开做过一次，插件测试 7 条用例在第一次写入时全红。
- **状态清单的唯一落点**：`packages/agent-core/src/state/sessionSlots.ts:105-129` 的 `SESSION_SLOTS`。它同时是快照字段名、事务日志 `op.key`、清空动作和 applier 注册名的来源。
- **UI 侧入口**：`apps/web/src/main.tsx:117-122`（配 driver）→ `:125` `core.persistence.hydrate()` → `:126` 没恢复出会话才 `newSession()`。

## 数据怎么走（一次真实写入，追到底）

1. **命令层**：`packages/agent-core/src/runtime/commands/runLifecycleCommands.ts:49` `sendMessage` 从 root store 取 `activeSessionIdAtom`（`:50`）与 `sessionsAtom[id]`（`:54`），run 在飞就把输入排队（`:73-80`），否则 `:91` 起 run。命令**自己不碰 atom**，只调写入器。
2. **写入器**：`packages/agent-core/src/state/sessionWriters.ts:86-92` `appendItem` 先做 ghost guard（`:34-36`：会话没在 root store 登记就 no-op），再 `appendItemToSession`，最后 `touchSession` 把 root 里的 `updatedAt` 前进（`:43-54`）。
3. **记账形态分岔**：`items` 走增量而非整值（`sessionWriters.ts:63-67` → `packages/agent-core/src/state/sessionItemsLog.ts:26-28` → `packages/agent-core/src/state/listSlotLog.ts:122-130`）。一条 `append` op 只记 `{key:'items:append', scope: 条目 id, before: undefined, after: 这一条}`。整值那条路是 `packages/agent-core/src/state/sessionSlotWrite.ts:49-76` 的 `writeSlot`：先短路值没真变的写入（`:70`），再在一个事务里 `store.setter` + `history.record({key, before, after})`（`:72-75`）。
4. **事务与轮标签**：两条路共用 `sessionSlotWrite.ts:85-95` 的 `inTurnTransaction`，标签取写入**之前**的 `runAtom.turnId`（`:98-100`）。`transaction()` 是同步的而一轮是异步的，所以「一轮 = 一个事务」做不到，改成「同一轮的条目带同一个标签，撤销时弹到标签变化为止」（理由在 `:18-24`）。
5. **落盘栅栏**：`core.persistence.persistRecovery(id, reason)`，全仓 23 个调用点、13 个文件（如 `packages/agent-core/src/runtime/toolCallExecutionFence.ts:15` 工具执行前、`packages/agent-core/src/runtime/toolLoopSupport.ts:77` 工具结果回填后）。它进 `packages/agent-core/src/runtime/persistenceBridge.ts:179-188`：先由 recoveryWriter 同步 capture + 排队写快照，写成功后 `flushHistoryLog`。
6. **快照怎么捕**：`packages/agent-core/src/state/recoveryProjection.ts:68-100` `captureRecoverySnapshot` 同步读 10 个槽位、剥掉进程本地的 `pendingExecutionId`（`:54-58`），JSON 往返 + codec 双向验证（`:46-52`）。generation 由 `packages/agent-core/src/runtime/recoveryWriter.ts:176-182` 在 capture 那一刻分配，落盘冲突时 `:130-135` 重取。
7. **账跟着快照走**：`persistenceBridge.ts:161-177` —— **只在 `outcome.status === 'saved'` 时**把 `history.getState()` 整份刷出，并存下那次快照的 `generation` 与当前 undo 屏障（`:169-173`）。不可 JSON 序列化就整份丢掉（`:174-176`）。为什么不用 einfach 的 `HistoryPersistPort` 增量镜像：`packages/agent-core/src/state/persistence/historyLogDriver.ts:3-21`——它逐笔跟随内存，而快照只在栅栏落盘，时点不一致时 undo 会把更早状态的 `before` 写进当前世界。
8. **重启回来**：`packages/agent-core/src/state/persistence/hydrate.ts:154` `hydrateForCore` → `:176` 读会话列表与每会话快照 → `:207-219` 铺 root store → `:228-231` 每会话 `applyRecoverySnapshot`（`recoveryProjection.ts:104-118` 一个命令 atom 把 10 个槽位写在同一次 flush 里），进程遗留的 `running/awaiting_tool` 在 `packages/agent-core/src/state/persistence/recoveryHydration.ts:62-86` 统一归成 `interrupted` → `:235-243` 再铺日志 → `:247` 没有快照的会话 `clearRecoveryProjection` 推回默认值（fail-closed）。
9. **日志配对判据**：`hydrate.ts:132-149` —— `log.generation !== snapshotGeneration` 就整份丢弃；`history.hydrate()` 只在空栈上合法，所以顺序必须是「先铺状态（不记账）、再铺日志」（`:232-233`），而日志读回是 await 的一步、必须在放行编辑之前（`:251-253`）。屏障在 `hydrate()` 成功之后才 `restoreUndoBarrier`（`:145`）。

## 每部分负责什么 / 状态归谁 / 谁能调谁

| 部分 | 职责 | 持有的状态 | 谁可以调它 | 不许做 |
|---|---|---|---|---|
| 界面 store `apps/web/src/uiStore.ts:17` | 渲染态，判据「刷新丢了也没人发现」（`:3-4`） | 设置/MCP/插件/trace viewer/草稿/附件/滑动窗口，约 70 个 atom 构造点，全在 `apps/web/src` 内 | 任何组件裸 `useAtomValue` | 不进快照、不进账、不按会话分桶 |
| core root store `packages/agent-core/src/state/rootAtoms.ts` | 跨会话登记表 | 11 个 atom（8 primitive + 3 derived）：工作区、会话元数据、当前会话 id | 组件经 `useRootAtomValue`；core 内部直接持 | 不放任何 `Record<sessionId, 会话内容>`（`state/rootStore.ts:6`） |
| per-session agent store | 一个会话的全部运行态 | 21 个会话 atom，其中 10 个是槽位 | 组件经 `useAgentAtomValue`；写只走 writer/command | 组件不得裸读（读到默认值不报错） |
| `state/` 写入器 | 改会话 atom **并**记账 | 无 | `runtime/commands/`、runtime、插件（经 `CoreCtx`） | 不得跳过 `writeSlot` / `*Logged` 直接 `store.setter` 槽位 atom |
| `runtime/commands/` 13 个模块 | UI 的唯一写入面 | 无 | UI、宿主 | 不得把 `History` 本体交给渲染层（`runtime/commands/sessionScopeCommands.ts:32-34`） |
| `SessionHistory` | 账本 + 一个可用态派生 atom | entries/cursor（住在该会话 store） | 命令层 | UI 不得拿到（只交出 `undoAvailabilityAtom`） |
| persistence bridge | 栅栏与读回 | driver 引用 | runtime、宿主装配 | `recoveryStore`/`historyFor` 只返回已存在的会话，落盘绝不复活幽灵会话（`persistenceBridge.ts:44-49`） |

**三层 store 的物理边界**：生产里 einfach 的环境 `<Provider>` **只有一处**——`apps/web/src/main.tsx:75` 绑 `uiStore`；`RootStoreProvider` 包在它里面（`:76`）；`AgentStoreProvider` 不在根上，由 `apps/web/src/agentNew/ui/ActiveSessionProvider.tsx:56` 按会话绑、`key={id}` 整体重挂。`packages/agent-react/src/coreStoreBindings.tsx` 用两个独立 React context 传 store（`:24-25`），读值走 `useAtomValue(atom, { store })`（`:57-59`、`:62-64`），**没有 Provider 直接抛**（`:43-46`），且刻意不提供 setter（`:16-18`）。方向是刻意的（`main.tsx:68-70`）：环境给界面 → 漏改一处是「core atom 读到默认值」，会话列表当场空掉；反过来漏改毫无症状。

**切会话清哪些**：`apps/web/src/agentNew/ui/sessionScopedViewState.ts:19-29` 清 4 个界面 atom——`composerDraftAtom`(`:20`)、`composerImageAttachmentAtom`(`:24-26`，`revision+1` 让在飞的准备结果按版本作废)、`messageWindowAtom`(`:27`)、`planTraceWindowsAtom`(`:28`)。唯一调用点 `ActiveSessionProvider.tsx:47`，`useEffect` 依赖 `[id, uiStore]`。展开折叠态不清，因为按 group/stage id 索引、换会话自然查不到旧 key（`:3-5`）。
